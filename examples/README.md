# MCP Portico examples

This directory is a complete, runnable walkthrough of the MCP Portico flow:
import a public OpenAPI API into an inert catalog, validate a multi-tenant
registry that pins it by checksum, create Portico API keys, serve the MCP
endpoint, and drive a session over HTTP.

The same MCP session flow applies to any MCP-compatible AI application -
coding assistants, support agents, finance and operations agents, workflow
agents, and custom MCP hosts. The [domain use cases](use-cases/README.md)
demonstrate the fixed toolset and confirmation semantics on non-coding
domains, with fixture catalogs and a clear split between generic MCP
behavior and backend-specific catalog configuration.

Files:

- `apis/petstore.openapi.yaml` - a public OpenAPI 3.0 API (Petstore Lite):
  `pets.list`, `pets.create`, `pets.get`, `pets.delete`, and a public
  `health.get`. Pets routes declare the `bearerAuth` (`http`/`bearer`)
  security scheme.
- `apis/petstore.catalog.json` - the compiled catalog v2 artifact for the
  Petstore Lite API. It is generated by the import command below and is kept
  identical to the CLI output except for the `provenance.generatedAt`
  timestamp; the catalog checksum excludes that volatile field, so re-imports
  validate against the same pinned checksum.
- `sample-catalog.json` - a compiled catalog v2 artifact (billing API) that
  passes `mcp-portico catalog validate`.
- `sample-overlay.json` - a policy overlay v1 that restricts and annotates
  operations during compilation.
- `sample-registry.yaml` / `sample-registry.json` - the same registry in YAML
  and JSON: two tenants, two backends (petstore + billing), seven
  connections, and every upstream auth provider type.
- `use-cases/` - credential-free domain examples (support, operations and
  finance, workflow with confirmation) with OpenAPI fixtures, compiled
  catalogs, and a registry pinned by checksum.

The integration test `test/integration/examples.test.ts` executes the import,
validation, serve, and MCP session steps of this walkthrough end-to-end
against a loopback upstream. `test/integration/use-cases.test.ts` does the
same for the domain use cases.

## Domain use cases

The walkthrough below drives one MCP session against the Petstore Lite API.
The flow is identical for every client domain; only catalog and registry
configuration changes per backend.

- [Support agent](use-cases/support-agent.md) - a service-desk agent searches
  tickets and reads customer profiles through catalog-gated operations.
- [Operations and finance](use-cases/operations-finance.md) - a finance agent
  reads approved internal data without ever seeing a database or service URL.
- [Workflow with confirmation](use-cases/workflow-confirmation.md) - a
  workflow agent creates an invoice and confirms the mutation with a token.
- [Weather-aware market brief](use-cases/weather-market/README.md) - an MCP
  host joins live weather, crypto-market, and FX data into one dated research
  brief.

See [use-cases/README.md](use-cases/README.md) for the shared principles and
the split between generic MCP behavior and backend-specific catalog
configuration.

## 1. Prerequisites

- Node.js 22 or newer
- pnpm (this repository is pinned to `packageManager: pnpm@11.9.0`)

## 2. Build

```bash
pnpm install
pnpm build
```

`pnpm build` compiles the TypeScript sources to `dist/`, which is what the
`mcp-portico` executable runs. From here on, `mcp-portico` means
`pnpm exec mcp-portico` (or `node dist/cli/index.js`).

## 3. Import the public API

Compile the Petstore Lite OpenAPI document into an inert, credential-free
catalog v2 artifact plus an import report:

```bash
mcp-portico catalog import examples/apis/petstore.openapi.yaml \
  --api-id petstore \
  --output examples/apis/petstore.catalog.json \
  --report /tmp/petstore.report.json
```

The checked-in `examples/apis/petstore.catalog.json` is generated this way.
Re-running the command reproduces it identically except for the
`provenance.generatedAt` timestamp, and `mcp-portico catalog diff` reports no
differences because the checksum ignores volatile provenance fields. Import
never creates or updates registry state: a backend becomes reachable only
after an operator pins its catalog checksum and creates tenant-owned
connections.

## 4. Validate the artifacts

```bash
mcp-portico catalog validate examples/apis/petstore.catalog.json
mcp-portico registry validate examples/sample-registry.yaml
```

The registry validator checks the JSON Schema, referential integrity,
connection policies, and that every backend `catalogRef` exists and its
`catalogChecksum` matches the catalog on disk. `examples/sample-registry.json`
is the same registry in JSON.

## 5. Create Portico API keys

Portico clients authenticate with `mpp_<key-id>_<secret>` bearer tokens. The
registry stores only the public key id and an HMAC digest keyed by the
`MCP_PORTICO_KEY_PEPPER` environment variable; the plaintext token is printed
once and never stored.

```bash
export MCP_PORTICO_KEY_PEPPER='replace-with-a-long-random-pepper'

mcp-portico key create --registry examples/sample-registry.yaml \
  --tenant acme --principal acme-automation

mcp-portico key create --registry examples/sample-registry.yaml \
  --tenant globex --principal globex-automation
```

Each command updates the registry file in place with the principal's key id
and digest, then prints a token. Capture both tokens; you will use them as
the `$ACME_TOKEN` and `$GLOBEX_TOKEN` variables below. Re-running `key
create` rotates the key and invalidates the previous token. Use the same
`MCP_PORTICO_KEY_PEPPER` value for key creation and for `serve`, and keep it
secret.

## 6. Serve

Export every environment reference used by the registry connections
(placeholders are fine for this walkthrough; the sample connections point at
`https://example.com`), then start the server:

```bash
export MCP_PORTICO_PORT=3000
export MCP_PORTICO_AUTH_MODE=bearer
export ACME_PETSTORE_TOKEN='replace-with-an-upstream-token'
export GLOBEX_PETSTORE_TOKEN='replace-with-an-upstream-token'
export GLOBEX_PETSTORE_USERNAME='replace-with-an-upstream-username'
export GLOBEX_PETSTORE_PASSWORD='replace-with-an-upstream-password'
export ACME_BILLING_API_KEY='replace-with-an-upstream-key'
export GLOBEX_BILLING_API_KEY='replace-with-an-upstream-key'
export ACME_PETSTORE_PARTNER_KEY='replace-with-an-upstream-key'
export ACME_TOKEN='<paste-the-acme-key-from-step-5>'
export GLOBEX_TOKEN='<paste-the-globex-key-from-step-5>'

mcp-portico serve --registry examples/sample-registry.yaml
```

`MCP_PORTICO_PORT` is optional (the server binds `127.0.0.1:3000` by
default); the `--port` flag overrides it. The server validates the registry
and all secret references at startup and refuses to start if anything is
missing. `MCP_PORTICO_AUTH_MODE=bearer` enables Portico API-key
authentication (the default `none` mode is for loopback-only development
without client identity). Keep the server running in this terminal for the
next step.

## 7. MCP session over HTTP

From a second terminal, run an MCP session against the server. The toolset is
fixed: `list_connections`, `select_connection`, `get_session`,
`search_operations`, `describe_operation`, `call_operation`,
`call_operations`, and `test_connection`.

Initialize the session:

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"walkthrough","version":"0.0.0"}}}'
```

Send the initialized notification (HTTP 202, no body):

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
```

List the available tools:

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
```

Select the acme petstore connection to create the session:

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"select_connection","arguments":{"connectionId":"acme-petstore-prod"}}}'
```

Call `pets.list` (a read operation):

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"call_operation","arguments":{"operationId":"pets.list","arguments":{"limit":5}}}}'
```

Call `pets.create`. Write operations return a confirmation token on the
first call:

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"call_operation","arguments":{"operationId":"pets.create","arguments":{"body":{"name":"Rex","tag":"dog"}}}}}'
```

Repeat the call with the confirmation token from the response:

```bash
curl -sS --max-time 30 "http://127.0.0.1:$PORT/mcp" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $ACME_TOKEN" \
  -d '{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"call_operation","arguments":{"operationId":"pets.create","arguments":{"body":{"name":"Rex","tag":"dog"}},"confirmationToken":"<paste-the-token-from-the-previous-response>"}}}'
```

The sample connections point at `https://example.com` placeholders, so the
calls exercise the full gated pipeline (authentication, session
authorization, confirmation, argument validation, network policy, and
auditing) against a placeholder upstream. To see a real upstream response,
point a connection's `baseUrl` at your own deployment, or run
`test/integration/examples.test.ts`, which drives the same session flow
against a loopback petstore server.

You can repeat the session with the globex token; `globex-automation` is
authorized for `globex-petstore-prod`, `globex-billing-prod`, and
`globex-petstore-basic`, and cannot select any acme connection.

## 8. Inspector

The read-only inspector is served by the same process. Open it in a browser
with the acme API key:

```text
http://127.0.0.1:3000/inspector
```

Or query its tenant-scoped API directly:

```bash
curl -sS --max-time 30 -H "authorization: Bearer $ACME_TOKEN" \
  "http://127.0.0.1:$PORT/inspector/api/overview"
```

The inspector returns only the authenticated tenant's connections, catalog
metadata, health, and audit activity, with secret values redacted.

## 9. Upstream auth providers in this registry

Every connection references its credentials via `env:` variables; no secrets
are stored in the registry.

| Connection              | Tenant | Backend  | Upstream auth                   | Secret source                                                  |
| ----------------------- | ------ | -------- | ------------------------------- | -------------------------------------------------------------- |
| `acme-petstore-prod`    | acme   | petstore | bearer                          | `env:ACME_PETSTORE_TOKEN`                                      |
| `acme-billing-prod`     | acme   | billing  | apiKey (header `X-API-Key`)     | `env:ACME_BILLING_API_KEY`                                     |
| `acme-petstore-public`  | acme   | petstore | none                            | -                                                              |
| `acme-petstore-partner` | acme   | petstore | staticHeaders (`X-Partner-Key`) | `env:ACME_PETSTORE_PARTNER_KEY`                                |
| `globex-petstore-prod`  | globex | petstore | bearer                          | `env:GLOBEX_PETSTORE_TOKEN`                                    |
| `globex-billing-prod`   | globex | billing  | apiKey (query `api_key`)        | `env:GLOBEX_BILLING_API_KEY`                                   |
| `globex-petstore-basic` | globex | petstore | basic                           | `env:GLOBEX_PETSTORE_USERNAME`, `env:GLOBEX_PETSTORE_PASSWORD` |

The Petstore Lite spec declares `bearerAuth` as the primary security scheme
on the pets routes. Because it also lists an empty security alternative, one
catalog can demonstrate every upstream auth provider, including `none` and
`staticHeaders`. The billing catalog demonstrates `apiKey` in both a header
and a query parameter. In a real deployment, match each connection's auth
type to the security requirements your API actually enforces.
